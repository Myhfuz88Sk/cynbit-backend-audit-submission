## 7. Backend review criteria

The following items are recommendations for further verification. They are not confirmed vulnerabilities in Cynbit's website.

### 7.1 Input validation

- Validate all submitted fields on the server, even if browser-side validation exists.
- Apply appropriate length limits and reject malformed input.
- Validate email addresses and handle unexpected content types safely.
- Avoid reflecting untrusted input into HTML or error messages.

### 7.2 API design and error handling

- Document expected HTTP methods, request schemas, response formats, and status codes.
- Return consistent, non-sensitive error messages.
- Avoid exposing stack traces, internal paths, secrets, or infrastructure details.
- Apply request timeouts and sensible body-size limits.

### 7.3 Abuse prevention

- Consider rate limiting and spam protection for inquiry and application endpoints.
- Use bounded retries and avoid retrying non-idempotent requests without safeguards.
- Monitor unusual request patterns without collecting unnecessary personal information.

### 7.4 Privacy and data protection

- Collect only information required for the stated purpose.
- Restrict access to inquiry and applicant records using least privilege.
- Define retention and deletion procedures.
- Avoid recording full form submissions, credentials, tokens, or other sensitive values in application logs.

### 7.5 Performance and reliability

- Measure response times, payload sizes, and failure rates before making optimization decisions.
- Use caching only where appropriate for the content and privacy requirements.
- Monitor server-side errors and latency using structured, privacy-conscious logs.
- Test reliability under authorized, controlled conditions before considering production changes.

### 7.6 Verification priorities

1. Safely document the actual request and response for public page loads.
2. Verify form validation and submission behavior only with authorization and appropriate test data.
3. Review server-side validation, access controls, abuse prevention, and data handling if authorized source code or backend access becomes available.
4. Record each finding with evidence, impact, confidence, and a practical remediation.

- API contract: suitable HTTP methods/status codes, content types, consistent response schema.
- Validation: server-side schema, length limits, malformed JSON handling.
- Security: no secrets in client bundles/responses; least privilege; CSRF controls where relevant.
- Privacy: data minimization, retention rules, safe logs.
- Abuse prevention: body-size limits, rate limiting, timeouts, bounded retries.
- Reliability: correlation IDs, safe errors, monitoring.
- Performance: measure request timing and payload size before optimizing.

## 8. Limitations

This assessment is a preliminary review of publicly accessible website content and selected browser Network observations. It is not a penetration test, source-code review, infrastructure audit, or compliance assessment.

The following areas remain unverified:

- Actual backend architecture and API implementation.
- Server-side input validation and access controls.
- Form submission behavior, persistence, and data retention.
- Rate limiting, anti-spam controls, and abuse prevention.
- Authentication, authorization, and internal service configuration.
- Production performance, availability, and resilience.

The contact form was not submitted during this review. No confirmed security vulnerabilities are reported in this assessment. Absence of visible evidence does not establish that a security control is missing.

Further verification should be performed only with appropriate authorization and, where necessary, access to source code, system documentation, or a designated test environment.
